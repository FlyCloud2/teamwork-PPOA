## 3. 关键发现：三个 β 设置得到的是同一条轨迹

`adaptiveKL`、`adaptiveKL-capped`、`adaptiveKL-tight` 的 `progress.csv`
**除了最后一列 `wall_time_s` 之外逐行相同**（可用下面的命令自查，输出应为 0）：

```bash
diff <(cut -d, -f1-10 runs/<A>/progress.csv) <(cut -d, -f1-10 runs/<B>/progress.csv) | wc -l
```

β 相差 150 个数量级，训练轨迹一模一样。这不可能是巧合，只能说明一件事：
**在这套设置下，β 的大小对更新方向没有影响。**

推断（这是分析，不是测量）：当 β·KL 的梯度远大于策略项梯度时，
`nn.utils.clip_grad_norm_(0.5)` 会把每一步归一化成「沿 KL 下降方向、步长 0.5」，
与 β 的具体数值无关。也就是说，`kl-penalty` 变体退化成「只最小化 KL、几乎不优化策略」，
策略因此停在一个低回报处。这也解释了它为什么稳定地低于 `clip0.2`。

**这一条修正了本节初稿的判断**：问题不在 β 后来涨到多大（1e150），
而在 β = 1 时罚项就已经主导了被裁剪后的梯度。

## 4. 对论文 claim 的裁决

论文 Table 1 的主张是一个**排序**：裁剪（ε=0.2，0.82）> 自适应 KL（d_targ=0.01，0.74）> 不裁剪（−0.39）。

| 子claim | 我们的结果 | 裁决 |
|---|---|---|
| 裁剪优于不裁剪 | 三个环境全部成立，且差距远超种子波动 | **支持** |
| 裁剪优于自适应 KL | 三个环境全部成立 | **支持** |
| 自适应 KL 优于不裁剪 | HalfCheetah 596 vs 375、Hopper 480 vs 355 成立；Walker2d 210 vs 262 不成立（在 std 内） | **部分支持** |
| 自适应 KL 是一种有效的、可训练的代理目标 | 在我们的实现下它退化成了「只降 KL」，回报稳定偏低 | **无法判定（inconclusive）** |

因此整体裁决：**部分复现**。论文"裁剪最强、不裁剪最弱"的两端成立；
中间那一档我们没能得到一个可用的实现，所以无法据此确认或否定论文对它的排序。

## 5. 局限（必须写进报告）

1. **绝对分数与论文不可比**：环境 wrapper（观测/奖励归一化与裁剪）、MuJoCo 3.1.6、
   gymnasium 0.29.1 都与论文不同，每一处已记入 `docs/deviations.md`。我们只解读排序。
2. **自适应 KL 这一档是我们实现的**，不是官方代码。它与论文 Algorithm 2 的差异
   （β 上界的引入、以及 β 主导后与梯度裁剪的相互作用）都写在 `MODIFICATIONS.md` 和偏差表里。
3. **单种子 1M 步的方差很大**（例如 clip0.2 在 HalfCheetah 上从 1247 到 3098），
   所以三轮子只能支撑方向性判断，不能支撑小数点级的结论。
4. `clipfrac` 在 `kl-penalty` 下只是诊断量（比值跳出 0.2 带的比例），不是损失项。

## 6. 复现方式

```powershell
# 主矩阵 27 次（3 变体 × 3 环境 × 3 种子）
python scripts/run.py --variant clip0.2      --env HalfCheetah-v4 --seed 0 --threads 1
# 受控对照各 9 次
python scripts/run.py --variant adaptiveKL-capped --env HalfCheetah-v4 --seed 0 --threads 1
python scripts/run.py --variant adaptiveKL-tight  --env HalfCheetah-v4 --seed 0 --threads 1
# 校验、汇总、出图
python scripts/verify_runs.py --run runs/<run_id>
python scripts/summarize_c1.py      # -> logs/c1_summary.json
python scripts/plot_c1.py           # -> figures/c1_variants.png, c1_curves.png
```

`logs/c1_summary.json` 由 `scripts/summarize_c1.py` 从这些 CSV 生成，
本文件与报告中的所有数字都来自它。重跑该脚本得到逐字节相同的文件
（可用 `git status logs/c1_summary.json` 自查：应为无改动）。
